# Communication

## What interviewers evaluate

- Clarity: answering the actual question, leading with the main point.
- Structure: organizing an answer into a few clear parts.
- Adapting to the audience: explaining technical ideas to non-technical people.
- Conciseness: no rambling, and few filler words.
- Listening: asking clarifying questions and checking understanding.

## Question bank

### Junior

#### Explain your final-year project to someone non-technical.

**Strong answer includes:** starts with the problem and who it helps, uses an everyday analogy, avoids
jargon or defines it, describes the result in terms of impact, and keeps it under two minutes.

**Common weak answers:** starts with the tech stack and model architecture.

**Red flags:** cannot simplify; gets frustrated with follow-up questions.

#### How do you ask for help when you are stuck?

**Strong answer includes:** first timeboxes their own attempt, then asks with context: the goal, what
they tried, the exact error, and a specific question; respects the other person's time; shares the
solution afterwards.

**Common weak answers:** "I just ask my senior."

**Red flags:** either never asks or asks without trying anything.

### Mid

#### How do you communicate a delay or bad news to a manager or client?

**Strong answer includes:** tells them early, states the impact plainly, explains the cause briefly
without blame, offers options with tradeoffs (cut scope, extend date, add help), and follows up
in writing.

**Common weak answers:** waits until the deadline.

**Red flags:** hides problems or blames others.

#### How do you write good technical documentation?

**Strong answer includes:** knows the audience, starts with purpose and a quick start, uses short
sections and examples, keeps docs next to the code and updates them with changes.

**Common weak answers:** "I write comments in the code."

**Red flags:** thinks documentation is unnecessary.

## Scoring anchors

Example question: "Explain what an API is to a non-technical person."

### Score 1/5

"An API is an application programming interface using REST endpoints with JSON payloads over
HTTP." Jargon only, not adapted to the audience.

### Score 3/5

"It's a way for two programs to talk to each other." Correct but abstract, no example.

### Score 5/5

"Think of a restaurant waiter. You don't go into the kitchen; you tell the waiter what you want,
and they bring it back. An API is the waiter between apps: when a weather app shows today's
forecast, it asked a weather service's API and got the answer back." Clear analogy, concrete
example, concise.

## Communication guidance for spoken answers

- Lead with the answer, then support it ("In short, X. Here's why...").
- Use signposting: "There are three parts: first, ...".
- A comfortable speaking pace is roughly 120 to 160 words per minute.
- Replace filler words (um, like, basically) with a short silent pause.
